# Manual encrypted mobile transfer

The iPhone/iPad app supports user-initiated encrypted files through Files. It does
not run a synchronization service, upload memory itself, retain a passphrase, or
transfer model weights or account access. A Files provider selected by the user
may download or upload files. Choose **On My iPhone** or a local destination for
offline storage and move the resulting file through a trusted channel.

## Choose the right format

- **Full encrypted mobile backup** contains all project notes and chats. Its
  `VEYRA-MOBILE` v1 envelope is for this compatible mobile app. The desktop
  companion does **not** import this format.
- **Encrypted notes for desktop (no chats)** contains all project notes, their
  IDs, source labels, and timestamps. Its `VEYRA-MEMORY` v1 envelope and record
  schema match `companion/sync.py`. Chats are deliberately excluded. The mode
  picker and confirmation identify this omission before export.
- Import accepts either format and shows note/chat counts after authentication.
  Nothing changes until **Merge memory** or **Restore memory** is confirmed.

No Android encrypted importer is implied by these formats. They are not an
automatic, continuous, or bidirectional synchronization protocol.

## User flow

1. Open Offline memory → Encrypted transfer.
2. Choose full mobile backup or desktop notes. Enter and repeat a unique
   passphrase of at least 12 characters. A longer random multiword passphrase is
   strongly recommended. Review the all-projects export confirmation.
3. Choose where to save the encrypted `.veyra` file. Keep the passphrase separate
   from the file. There is no recovery mechanism for a forgotten passphrase.
4. On the receiving mobile app, choose the encrypted file, enter its original
   passphrase, and select **Unlock and review**. Verify the counts and confirm.
5. For the desktop companion, use its existing `export-memory` / `import-memory`
   commands (see `python -m companion --help`) and its interactive passphrase
   prompt. Desktop → mobile transfers must contain mobile-compatible notes.

The passphrase fields are cleared when used, canceled, dismissed, or backgrounded.
Unconfirmed plaintext previews are also discarded when canceled, dismissed, or
backgrounded. Expensive key derivation and provider reads run away from the UI
actor. Cancellation prevents stale results from importing or presenting files;
it cannot forcibly interrupt a synchronous system KDF or a file provider's work
already underway. The app never writes a plaintext temporary transfer file.

## Compatibility and validation limits

The mobile importer enforces its existing 5,000,000-byte JSON backup limit,
10,000-note and 10,000-chat limits, unique UUID IDs, valid roles, and field limits:
project ≤300 Swift characters, source ≤2,000, note text ≤20,000, chat text ≤100,000.
Encrypted desktop input is capped at 8 MiB and its converted mobile backup must
still fit the mobile limit. Oversized input is rejected before expensive work
where its envelope permits this, and every file read is bounded.

Desktop interoperability additionally requires:

- Canonical lowercase hyphenated UUID record IDs, as generated by `Memory.add`.
  Arbitrary legacy IDs or differently cased UUID strings are rejected rather
  than silently remapped.
- Nonempty project, body, and source strings, each ≤65,536 UTF-8 bytes, plus all
  mobile field limits and both platforms' possible-credential checks.
- Finite Unix timestamps between 0 and 253402300799. Mobile `Date` values are
  converted from/to Unix seconds explicitly; mobile JSON's reference epoch is
  2001-01-01, not 1970-01-01.
- Version 1 with the exact expected top-level and record keys. Unknown fields,
  invalid record types, duplicate IDs, or an incompatible record reject the
  entire import. JSON parsing uses Apple's decoders; duplicate JSON object keys
  are not independently detected on mobile, unlike the desktop parser.

Validation and decryption do not access the memory store. Wrong passphrases,
authentication failures, malformed content, and incompatible records cannot
partially import memory. After confirmation, the existing store imports the
fully validated backup with its normal atomic persistence/recovery path.

On mobile, an existing record with the same ID is kept and the incoming record
is skipped, even when its contents differ. On desktop, the companion retains
conflicting contents using a deterministic alternate ID. Do not treat repeated
file transfers as edit reconciliation. Source provenance is untrusted metadata,
not proof of who authored a note; imported notes remain untrusted model context.

## Cryptographic envelope

Both supported formats use the same construction:

| Bytes | Meaning |
| --- | --- |
| 0–13 | `VEYRA-MOBILE\x00\x01` or `VEYRA-MEMORY\x00\x01` |
| 14–29 | Fresh random 16-byte salt |
| 30–41 | Fresh random 12-byte AES-GCM nonce |
| 42… | Ciphertext followed by its 16-byte authentication tag |

The 32-byte AES-256 key is derived with CommonCrypto PBKDF2-HMAC-SHA256 and
600,000 iterations. Passphrases are exact UTF-8, with no trimming or Unicode
normalization. Imports accept nonempty passphrases up to 4096 UTF-8 bytes to
remain compatible with desktop; new mobile exports additionally require at
least 12 characters and reject entirely whitespace input.

CryptoKit AES-GCM authenticates the entire 42-byte prefix as associated data.
`SecRandomCopyBytes` generates salt and nonce for every export. No configurable
KDF cost is accepted from an untrusted file. No custom cipher, hash, random
generator, or KDF implementation is used. Versioned headers distinguish the
schemas instead of guessing after decryption.

Encryption protects the exported file, not an unlocked device, an existing
unencrypted JSON backup, a weak/reused passphrase, or the selected provider's
metadata. Swift strings and framework internals can retain transient memory
copies; clearing UI state is not a guarantee of forensic zeroization. Temporary
key derivation byte buffers are reset where practical. No passphrase is logged,
stored in preferences/Keychain, or sent to the companion automatically. Secret
detection is only a warning layer and cannot identify all credentials.

## Integration

`App` and `Tests` are already folder sources in `project.yml`; these new Swift
files require no external packages. CommonCrypto, Security, and CryptoKit are
Apple SDK modules. Present this sheet from the memory UI:

```swift
.sheet(isPresented: $showEncryptedTransfer) {
    EncryptedTransferView(
        backupData: { try store.backupData() },
        importBackup: { data in
            store.error = nil
            store.importBackup(data)
            if let error = store.error { throw AppFailure.message(error) }
        },
        isRestoring: store.loadFailed
    )
}
```

The throwing adapter is required because the existing `importBackup` catches
errors internally. Without it, a persistence failure could be shown as success.
Only ciphertext goes to `EncryptedMemoryDocument` / `fileExporter`; no plaintext
backup should be placed into that exporter.

## Verification

Run native tests with the repository's generated Xcode project and Xcode 26.
`EncryptedTransferTests` covers independent Python-created mobile and desktop
fixtures, round trips, notes-only behavior, IDs/epochs/Unicode, random salt and
nonce, wrong passphrase, tampered header/salt/nonce/ciphertext/tag, incompatible
desktop rows, limits, symlink/regular-file checks, and bounded reads.

The desktop test retains an actual Swift-generated ciphertext attachment named
`swift-desktop-transfer.veyra`. After a successful native run:

```sh
xcrun xcresulttool export attachments --path TestResults.xcresult --output-path test-screenshots
python -m pip install -r companion/requirements-sync.txt
python Tests/verify_mobile_transfer.py test-screenshots
```

The Python verifier uses the real `companion.sync.import_snapshot` and checks
the note's fields, the absence of chat/task content, idempotence, corruption
rejection, and wrong-password rejection without mutations. It finds the fixture
by its header because xcresulttool may rename attachments. **Missing fixtures
exit nonzero**, so absent native execution cannot silently pass this check.
The test data and its passphrase are public and synthetic, never real memory.

For Linux-only validation:

```sh
python Tests/verify_mobile_transfer.py --self-test
python -m unittest discover -s companion/tests -v
```

`--self-test` independently decrypts the committed Python-generated reference
vectors and checks verifier failure paths. It does **not** execute Swift and is
not a substitute for the native → Python attachment check. Native builds,
simulator tests, and direct-device Files/lifecycle testing require Xcode/iOS and
must not be claimed to have passed from a Linux-only run.

Before release, check repeat export/import, wrong passphrase then retry, picker
cancellation, Cancel preparation, dismissal during KDF/provider reads,
backgrounding while confirmations are open, missing/offline providers, duplicate
IDs, failed persistence, corrupted-store restoration, and accessibility on a
real device. Do not publish or transfer real memory as a test fixture.
